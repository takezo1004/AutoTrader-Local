## 1. レイヤ構成

```

│    戦略の登録/解除・注文可否(戦略ごと「有効」)・自動運用・状態集約（dry-run/2段階は廃止＝2026-06-18）
├─ Engine 層（app/engine/）── 二刀エンジン
│    ├ StrategyLoader   フォルダから戦略を import（自己完結・_vlib一意キー）
```

## 2. ★二刀エンジン（D6）＝1つのロジック・2つの足供給源

戦略の約定モデルは共有 **PineBroker**（成行=次バー始値・指値/逆指値=イントラバー・3Split OCO・stop は次バーから有効）。これを2系統で駆動する：

| | オフライン driver（内蔵BT） | リアルタイム driver（ライブ） |
|---|---|---|
| 足供給 | 履歴 OHLC バー（全系列） | 形成中足の tick（1件ずつ） |
| 駆動 API | `run_pine_fast(strategy, df)` | `on_bar_close(確定足)` ＋ `on_tick(価格)` |
| 約定検知 | バーの高安で指値/逆指値（A2）・始値で成行（A1） | **tick がレベルに触れた瞬間に指値/逆指値**・新バー初tickで成行 |
| 戦略判断 | 確定足ごと（step/on_bar） | 確定足ごと（on_bar_close → on_bar） |
| 出力 | fills → 成績表 | fills → ポジション差分 → webhook（有効戦略のみ送出・無効は記録だけ） |
| 正本性 | golden 一致（検証基準） | 同一価格パスで オフライン と一致（[`03`](03_詳細仕様書.md) §B.5） |

- **戦略コードは1つ**（StrategyBuilder の `strategy.py` そのまま）。driver だけが違う。
- これは **TradingView の Strategy Tester（オフライン）／ライブ（リアルタイム）と同じ二重構造**。ブリッジ＝TV のブローカー（D7）。

## 3. Feed 層（ろうそく足生成）＝最重要・無傷保持（D13）

検証済み実装（`clone/feed`＝n225tradingAI2 由来）を**ベンダリングして無傷**で使う。改変は「外に出す口」の最小追加のみ（後述）。逐次アルゴリズムは [`03_詳細仕様書.md`](03_詳細仕様書.md) §C に**一字一句**。

### 3.1 構成（責務）
| モジュール | クラス/関数 | 責務 |
|---|---|---|
| `live_feed.py` | `LiveFeed`・`_handle`・`_on_line` | TCP5000 受信・JSON 解析・`update_ohlc` へ供給 |
| `ohlc_processor.py` | `OHLCManager`（singleton）・`update_ohlc`・`finalize_candle`・`bar_timer_loop`・`get_bar_times` | tick→15分足・確定足/ダミー足/**板寄せ特別足**・**on_bar_close コールバック** |
| `ohlc_storage.py` | `OHLCStorage`（singleton）・`add_to_candle`・`get_latest(n)`・`is_bar_completed` | 確定足キャッシュ（MAX 500）＋parquet 永続（**読込失敗で消さない**） |
| `market_session_manager.py`／`_market_hours.py` | `is_market_open`→`is_open_at`・`is_trading_time`(別名)・`is_no_trade_day`・カレンダー | 日中 08:45–15:45／夜間 17:00–翌06:00・**所有取引日ベース判定**（早朝0-6時=前日の夜間／大納会は夜間なし／年末年始／土日／カレンダーの実施しない）＝2026-06-27 是正（[`03`](03_詳細仕様書.md) §C.1.1） |
| `calendar_fetch.py` | `fetch_calendar(url)`・`update_calendar`・`ui_status`・`covered_years`・`CalendarFetchError` | JPX 祝日取引ページ取得（**複数年マージ**・確定/予定・`fetched_at`）／鮮度判定／取得元URLは settings 外出し（[`03`](03_詳細仕様書.md) §C.1.2） |
| `history_seed.py` | `seed_storage_from_kabu` | kabu CSV（≈335本）で warmup 300 を即充足 |

### 3.2 確定足の3種（[`03`](03_詳細仕様書.md) §C に詳細）
1. **通常確定足**：bar_end_time 到達で `current_candle` を確定。
2. **ダミー足**：tick が無い静かな窓 → 前足 close でフラット足。
3. **★板寄せ特別足（セッション末足）**：引け（`_is_session_close(bar_end_time)`＝終端が DAY_END 15:45 / NIGHT_END 6:00）で `bar_end_time` 付き特別足を1本立てる。**2026-06-26 是正＝(a) 引けの瞬間に市場クローズ扱いになっても必ず確定（旧版は壁時計＋市場ゲートで取りこぼし＝15:45/6:00 足が出ていなかった）／(b) 価格は実際の引け板寄せ約定値**＝`update_ohlc` が引け後最初に届く約定 tick をクローズ扱いでも1本だけ受け入れ、その値で特別足を立てる（実引け値 tick が `AUCTION_WAIT_SEC`=12秒 内に来ない静かな引けのみ `latest_price`＝引け直前値でフォールバック）。旧 `sleep(10)` は lock 保持で tick を遮断し空振りしていたため撤去。**(c) 出来高は引け板寄せ tick の volume を載せる（V=0 固定にしない・2026-06-26）**＝TS/TV と同じく板寄せ足に実出来高があり CMF 等が正しく使える。引け tick 無しの静かな引けのみ V=0（日次マージで上書き）。二重発火防止＝`_last_auction_dt`（同一引けは一度）＋`executed_time` を **finally で必ず False**（固着バグ修正）。境界時刻は決め打ちせず単一ソース `_market_hours`（§3.1）。**境界クランプ**（`end > s_end → end=s_end`）でセッション最後の足は短く切る。詳細＝[`03`](03_詳細仕様書.md) §C.2-4。

### 3.3 リアルタイムのための最小追加（唯一の改変）
- 既存は確定足の `on_bar_close` のみ公開し、**形成中足を外に出さない**。
- リアルタイム指値検知（D12）のため、**`update_ohlc` 内で `on_tick(price, tick_time)` コールバックを発火**する口を1つ足す（確定足経路・板寄せ・ダミー足は無傷）。RealtimeBroker がこれを購読して建ち注文を tick 判定する。
- ＝**「形成中足の現在価格を broker に渡す」最小 seam**。既存の足生成ロジックには触れない。

## 4. 戦略ローダ（StrategyLoader）

- 登録フォルダの `strategy.py` を**自己完結 import**（裸 import を避け、`importlib` で**戦略フォルダ単位の一意キー**＝`_v.<親>.<戦略名>.<module>`。多戦略同梱の module 名衝突を防ぐ。DT 実装の `_vlib` 方式と同一）。
- 取得：`build()` でインスタンス／`MANIFEST`（name/interval/warmup_bars/version）／`config.json`。
- **戦略は完全独立インスタンス**（モジュール可変状態なし）＝並行安全（Executor 順次≡並列）。

## 5. RealtimeBroker（ライブ駆動）

PineBroker をラップし、ライブの2イベントで駆動（詳細手順 [`03`](03_詳細仕様書.md) §B）：

- **on_bar_close(確定足)**：
  1. （前バー発注の）成行 pending を新バー初値相当で消化済みなら反映、建ち注文を確定足の高安で照合（オフラインと同じ A1/A2 をバー境界で再構成）。
  2. エンジン globals（`position_size`/`avg_price`/`entry_bar`/`bars_since_entry`）を戦略へ注入。
  3. `strategy.on_bar(bar)` → 注文リスト（entry/close/exit/cancel）を `submit`。
  4. ポジション/建ち注文の差分を WebhookConverter へ。
- **on_tick(price)**：形成中足の各 tick で**建ち注文（指値/逆指値）がレベルに触れたら即約定**→ ポジション更新 → WebhookConverter（イントラバー送出・D12）。成行 pending は新バー最初の tick で約定。
- 内部状態は PineBroker と同一（pos_dir/pos_qty/avg_price/entry_bar/_book/_filled_ids/_pending）。**ローカルが自前の建玉モデルを持つ**（TV と同じ・D7）。

## 6. WebhookConverter（ポジション差分→送出）

- PineBroker の約定イベント（fill）→ **ポジション遷移**（spec §9）に変換し送出。単一実装に集約（戦略ごとに重複させない）。
- 変換表（prev→cur）：新規/全量返済/**部分返済（3Split の1枚）**/ドテン/変化なし。`order_contracts`=増減枚数、`market_position_size`=発火後枚数。
- `order_price`：成行=0（ブリッジが対等価格）。指値 fill は**触れた価格**を載せても 0 でも可（ブリッジ忠実・D7）。既定は 0（既存 BridgeSender 流用）。詳細 [`03`](03_詳細仕様書.md) §G。
- **記録と注文の分離（2026-06-18）**：全戦略の**発火イベント（新規/決済）**は常時 `trade_log.jsonl` に記録（`RealtimeBroker.on_event`・sender 非依存）。**記録は「発火したか」だけが基準**＝ブリッジへ送出したか・enabled か・建玉化したかに**無関係**。**ブリッジへ注文を出すのは「有効」の戦略のみ**（`sender=BridgeSender`／無効は `sender=None`＝記録だけ）。旧 dry-run（グローバル仮想モード・VirtualSink）は廃止。
- **★再起動はウォームアップ・リプレイで復元（TV 同一シーケンス・2026-06-29 改訂）**：起動時に**履歴足を live と同一 `on_bar` でブローカー駆動（`RealtimeBroker.warmup_replay`）し、現在建玉・出口（部分約定含む）・指標バッファを履歴から再構築**する＝TV がロードのたび履歴から再計算するのと同じ。snapshot/restore（D15・2026-06-24 改訂の flat `prime`+`restore`）は**起動経路から不要**（メソッドは残置・建玉 JSON は受動記録のみ）。過去分は発注も記録もしない（webhook/取引イベント送出ゼロ）。これにより **BT(run_pine)≡live≡warmup が一致**。kabu 実弾整合はブリッジが担う（ローカルは戦略の建玉モデルを履歴から再構築し発火を忠実に出す）。詳細＝[`2026-06-29_warmup_replay_session_ohlc_reactivate.md`](2026-06-29_warmup_replay_session_ohlc_reactivate.md) ①。

## 7. Executor（並行）

- 既定 **SequentialExecutor**（決定的・デバッグ容易）。opt-in **ThreadPool**（numpy/pandas は GIL 解放で実効並列）。戦略が独立なので安全。1か所の seam。

## 8. Backtest 層（内蔵BT・オフライン駆動）

- **DataProvider**：蓄積 parquet（full-time）＋外部 CSV を**マージ**して半年窓 ＋ warmup を作る（[`03`](03_詳細仕様書.md) §F）。
- **実行**：`run_pine_fast(strategy(config), df)` → fills。
- **集計**：`summarize(fills)`（PF/勝率/純益/DD/平均保有/年別）＋ 月別・損益曲線・コスト感度（0/5/10pt）。
- **正本性**：golden（StrategyBuilder の result.md）と一致＝採用条件（D14）。

## 9. Controller・状態管理

- **Controller**（ヘッドレス）：登録/解除・注文可否（戦略ごと「有効」＝sender切替）・自動運用（起動時に start）・状態集約。再登録なしで即反映。（dry-run/2段階は廃止＝2026-06-18）
- **状態 JSON**（`app/state/`・スキーマは [`03`](03_詳細仕様書.md) §H）：
  - `registered.json`：登録戦略（フォルダパス・name・version・enabled）。
  - `engine_state.json`：稼働/停止・feed/ブリッジ接続・各戦略ポジ・直近シグナル・最終足時刻（ダッシュボードが1秒ごと読取。dry_run キーは廃止）。
- エンジンはヘッドレス（GUI を持たない）。ダッシュボードが唯一の操作面。

## 10. データ管理（蓄積・warmup・window）

- **常時蓄積**：`OHLCStorage` が確定足を parquet に追記（full-time ストア＝`n225tradingAI2/data/ohlc_data.parquet`・既存データ流用。無ければ製品内 data）。
- **★ライブ warmup＝戦略ごとの宣言本数（2026-08-10 改訂・決め打ち500の廃止）**：
  - 読み込み本数＝「登録戦略の manifest `warmup_bars` の最大（下限500）」（`controller._needed_warmup()`）。
  - **各戦略へのリプレイは `warmup_df.tail(その戦略の宣言本数)`**（宣言300の戦略は300本＝速く、
    宣言700の戦略は700本）。ready 判定・待機ログ表示も同じ宣言本数。
  - 呼び出し側（run_live/dashboard）から渡された warmup が不足なら `_topup_warmup_df` が
    ストアから読み直して補充（最新足を失わないよう末尾時刻が同等以上のときだけ差し替え）。
  - 背景＝旧実装は `get_latest(500)`/`tail(500)` の決め打てで、**宣言>500 の戦略（Swing_Ride 3本）が
    恒久待機＝記録もされない事故**が起きていた（2026-08-10 発見・是正。誤ログ「<300」も実数表示に修正）。
- **warmup**：起動時 kabu CSV で即充足（`history_seed`）。宣言本数未充足は発注抑止（建玉復元があれば ready）。
- **BT データ**：半年（≈数千本）は 500本キャッシュでは足りない → parquet 全体＋CSV マージから専用に読む（ライブ window とは別供給）。

### 12.1 命名・一貫性の軸（D9）
- **戦略名＝フォルダ名＝MANIFEST.name＝registered.json＝webhook alert_name＝ブリッジ登録名**（一意キー）。版は `manifest.json` の `version`（フォルダ名に入れない）。

### 12.2 ベンダリング配置（D1・跨ぎ import ゼロ）
| 配置先 | ベンダリング元 | 単位 |
|---|---|---|
| `app/feed/*` | `N225StrategyAI/clone/feed,live`（＝現 `_vendor/clone`） | ホストへ1式（**無傷**・on_tick の口だけ追加） |
