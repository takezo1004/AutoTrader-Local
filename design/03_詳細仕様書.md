## A. 注文プロトコルと約定モデル（PineBroker・転記）

戦略は確定足ごとに `on_bar(bar)`／`step(A,i)` で**注文リスト**を返す。種別：

```
{"t":"entry","dir":+1|-1,"qty":N,"comment":str}   成行・次バー始値（逆方向はドテン＝反対玉清算後に建てる）
{"t":"close","qty":N|None,"comment":str}          成行・次バー始値（None=全部。標準決済/EOD/SQ）
{"t":"exit","id":S,"qty":N|None,"limit":P,"stop":P,"comment":str}
                                                   建ち注文（OCO・毎バー上書き・各 ID 一度きり約定）
{"t":"cancel","id":S}                              建ち注文の取消
```
- 戦略はエンジン注入の `position_size`（符号付き枚数）/`position_avg_price`/`entry_bar`/`bars_since_entry` を読む（Pine の strategy.* 相当）。
- 約定（成行=次バー始値・指値=イントラバー・逆指値=イントラバー）は**エンジン（broker）の仕事**。戦略は注文を返すだけ。

### A.1 PineBroker の1バー3フェーズ（オフライン・転記）
`_engine/backtest.py::_run_pine` の各バー i：
1. **A1 `_exec_pending_market(o[i])`**：前バー発注の成行を当バー始値で約定。**close 群→entry 群の順**（ドテンで entry を先にすると新玉を後続 close が即閉じる「ゴーストトレード」になる）。
2. **A2 `_fill_resting(o,h,l)`**（`pos_dir!=0 and i>entry_bar`）：建ち注文（指値/逆指値）をイントラバー約定。
   - 指値（利確）：long は上・short は下。`o` が既に越え＝ギャップ始値約定、`h`/`l` が触れ＝指値約定。
   - 逆指値（損切/トレール）：long は下・short は上。同様にギャップ/逆指値。
   - 同バーに複数届く順：`up_first=(h-o)<(o-l)`（始値が高値寄り→上昇先行）。gap→進行方向の先行レグ→後行レグ、各レグ内は始値に近い順。
   - 約定した建ち注文は `_book` から消し、`_filled_ids` に記録（**現トレードで同 ID 再約定させない**）。
3. **B `submit(orders)`**：戦略が当バー終値で出した注文を登録（entry/close は `_pending`、exit は `_book` 上書き、cancel は削除）。`_filled_ids` の id は再アームしない（毎バー無条件再送出でも一度きり）。
- 建玉が無くなれば `_book`/`_filled_ids` を全消去（Pine 同様）。データ終端は最終足 close で強制決済（end_of_data）。

## B. リアルタイム tick ブローカー（ライブ・【新規】・肝）

オフライン A1/A2 は「バーの始値・高安」を使う。**リアルタイムは同じ判定を tick 列で行う**＝指値/逆指値が**実際にその価格へ触れた瞬間**に約定（D12・確定足の終わりを待たない）。PineBroker の状態（pos_dir/pos_qty/avg_price/entry_bar/_book/_filled_ids/_pending）を**そのまま**使い、駆動を2イベントにする。

### B.1 状態（PineBroker と同一）
```
pos_dir, pos_qty, avg_price, entry_bar, entry_ts, trade_id
_pending: list           # 次バー始値で約定する成行（close→entry 順）
_book: dict[id]->{qty,limit,stop,comment}
_filled_ids: set         # 現トレードで約定済み exit id
_bar_index               # 確定足の絶対 index（entry_bar 比較用）
_new_bar_first_tick      # 新バー最初の tick か（成行 pending の始値約定用）
```

### B.2 イベント①：`on_bar_close(candle)`（確定足ごと・戦略判断）
順序厳守：
1. `_bar_index += 1`。
2. **エンジン globals 注入**：`strategy.position_size/position_avg_price/entry_bar/bars_since_entry = …`。
3. `orders = strategy.on_bar(Bar(candle))`。
4. `submit(orders)`：
   - `entry`/`close` → `_pending`（次バー最初の tick で始値約定）。
   - `exit` → `_book` 上書き（`_filled_ids` の id は無視）。`cancel` → `_book` 削除。
5. `_new_bar_first_tick = True`（次に来る tick が新バー初値）。
6. ポジ/建ち注文の差分は基本ここでは送らない（指値はまだ約定していない）。**成行の予約だけ**は次の初 tick で約定→送出。
- ※確定足のH/Lで「このバー中に指値が約定したはず」を**再構成しない**（リアルタイムは tick で既に約定済みのため二重約定回避）。tick を取りこぼした保険として、確定足受領時に「未約定だが当バー高安が触れている建ち注文」を約定扱いにするフォールバックを置く（§B.6）。

### B.3 イベント②：`on_tick(price, tick_time)`（形成中足の各 tick）
```
# (1) 成行 pending を新バー最初の tick（=始値相当）で約定
if _new_bar_first_tick and _pending:
    _exec_pending_market(price)      # close 群→entry 群（A1 と同じ）→ 各 fill を webhook
    _new_bar_first_tick = False
# (2) 建ち注文を tick 価格で判定（pos_dir!=0 and _bar_index > entry_bar）
if pos_dir != 0 and _bar_index > entry_bar and _book:
    for id, od in list(_book):
        hit, px = _tick_hit(od, price, pos_dir)   # 指値/逆指値が price に触れたか
        if hit:
            _reduce(px, qty, ...); _book.pop(id); _filled_ids.add(id)
            -> webhook（部分返済 or 全量返済 / 触れた価格）
            if pos_dir == 0: break   # フラットになれば残りは _book ごと消滅
```
- `_tick_hit`（tick 版の A2）：
  - 指値：long は `price >= limit`、short は `price <= limit` で約定（約定価格＝limit。ギャップで一気に越えた tick でも limit で約定＝ブリッジが指値執行・保守側）。
  - 逆指値：long は `price <= stop`、short は `price >= stop`（約定価格＝stop。スリッページはブリッジ/kabu 実態）。
- **stop は次バーから有効**（`_bar_index > entry_bar`）＝建てた当日の足では建ち注文を約定させない（Pine 仕様・先読み防止）。
- 同 tick で複数 id が触れる場合：A2 と同じ優先順（gap→先行→後行）を tick 価格基準で適用。

### B.4 成行の送出タイミング（D12）
- 成行（entry/close/ドテン）：**新バー最初の tick で約定→即 webhook**（≒次足始値）。実装簡素化のため `on_bar_close` 時点で送ってもよい（ブリッジが忠実執行・差は1tick）。既定は**初 tick 送出**（始値に最も忠実）。

### B.5 ★オフライン＝リアルタイム 一致（検証で担保）
- 同一の価格パスを与えれば結果一致：**BT の各バーを「O→（H/L を上昇/下落先行順に）→C」の合成 tick 列に展開**して RealtimeBroker に流すと、`run_pine_fast` の fills と**トレード単位一致**するはず。これを単体テストにする（§J）。
- 完全一致しないのは実ライブのみ（tick の実順序・板寄せ・取りこぼし）。golden は基準値（D12）。

### B.6 取りこぼし・接続断のフォールバック（保険）
- tick が飛んで指値レベルを跨いだのに on_tick で捕捉できなかった場合に備え、**`on_bar_close` 受領時に「当確定足の高安が建ち注文レベルを越えているのに未約定の id」を約定扱い**にする（価格＝limit/stop）。＝オフライン A2 と同じ判定をフォールバックとして1回かける（二重約定は `_filled_ids` で防止）。

### C.1 セッションと境界（`get_bar_times`）＋ 市場OPEN判定・カレンダー
- 日中 08:45–15:45、夜間 17:00–翌06:00。`INTERVAL=15`。
- **★セッション境界時刻は決め打ちしない（2026-06-26・[[feedback_no_hardcoding]]）**：8:45/15:45/17:00/6:00 を `get_bar_times` 内にリテラルで持たず、市場時間の**唯一の正本** `_market_hours`（`is_market_open` と同一定義・元 config.py）の公開定数 `DAY_START/DAY_END/NIGHT_START/NIGHT_END` を `SESS_DAY_START/…/SESS_NIGHT_END` として参照する。**時刻リテラルを書いてよいのは正本 `_market_hours` の1箇所だけ**（許容形＝定数化＋根拠コメント）。`ohlc_processor`・`market_session_manager._fallback` とも**値を複製しない**（フォールバックで再宣言すると制度変更時に正本と静かにズレ＝損益直結のため、正本が読めなければ握りつぶさず ImportError 伝播／場況は安全側＝閉場）。制度変更（夜間 16:30→17:00・日中引け 15:15→15:45 等）は正本1箇所の修正で足窓・板寄せ・場況判定が一括追従する。ライブ feed は現行制度の tick のみ扱う（過去制度の時刻混在はバックテスト側の関心事）。
- バー境界は 15分グリッド。ただし**セッション境界でクランプ**：
  ```
  start = base.replace(minute=(minute//15)*15, second=0, microsecond=0)
  if start < s_start: start = s_start
  end = start + 15min
  if end > s_end:  end = s_end        # ★セッション最後の足は短く切られる
  ```
- 早朝 0:00–6:00 は**前日夜間の続き**（s_start＝前日17:00, s_end＝当日6:00）。隙間（15:45–17:00／6:00–8:45）は次セッション開始バーへ。
- ※既知バグ修正①：原版は夜間で session_start/end が誤値・else デッドコード → 当日境界で正しく書き直し済（転記版を使う）。

#### C.1.1 市場OPEN判定 `is_open_at`（2026-06-27・所有取引日ベース・厳密）
ろうそく足の取込/確定/ダミーは `market_session.is_market_open()`（→ `_market_hours.is_open_at(now)`）でゲートする。ナイトが日付をまたぐため、**時刻を所有する取引日**にセッションが立つかで判定する（暦日で判定しない）：

| 時間帯 | 所有取引日 | OPEN 条件 |
|---|---|---|
| 日中 08:45–15:45 | 当日 | `_day_session_held(当日)` |
| 夜間前半 17:00–24:00 | 当日 | `_night_session_held(当日)` |
| **夜間後半 00:00–06:00** | **前日** | `_night_session_held(前日)` |
| 場間（06:00–08:45 / 15:45–17:00） | — | 常に閉場 |

- `_day_session_held(d)` ＝ `not is_no_trade_day(d)`。`is_no_trade_day` ＝ **土日 ∪ 年末年始恒久休場 `{1/1,1/2,1/3,12/31}` ∪ カレンダーの「実施しない」**。祝日取引「実施する」日・通常平日は True。
- `_night_session_held(d)` ＝ `_day_session_held(d) and not 大納会(d)`。**大納会（年末最終取引日）は日中のみ・ナイト無し**（JPX。`_is_year_last_trading_day` で派生＝12月のデイ立会日で同年内に後続のデイ立会日が無い日）。
- 構造的な休み（土日・年末年始・大納会の夜間なし）は**コードの構造ルール**で持ち、カレンダーCSVには入れない（毎年不変・JPX 非掲載）。`_market_hours._fallback`（例外時の保険）も日付跨ぎ夜間だけは正しく扱う（カレンダー無し・週末のみ）。

#### C.1.2 市場カレンダーのライフサイクル（取得・フォーマット・運用・2026-06-27 確定）
カレンダーが持つのは**JPX が個別に決めた方針＝祝日ごとの「実施する/実施しない」だけ**（JPX 固有判断＝例 2026/11/23 注6・2027/9/20 注7 は規則から導けないため JPX が唯一の権威。jpholiday 等の自動導出は不採用）。

- **取得元**：JPX 祝日取引ページ（既定 URL＝`calendar_fetch.DEFAULT_JPX_URL`）。**将来 URL/ページ構造が変わる前提**で、実運用URLは `settings.json` の `jpx_calendar_url` に外出しし、ダッシュボードの[📅 カレンダー]ダイアログで**手動編集**できる（コード変更不要）。取得失敗（404/通信不可/表が無い）は `CalendarFetchError` を送出し「URLが変わった可能性があります。手動で設定してください」と案内（既存CSVは壊さない）。
- **取得方法**：`calendar_fetch.update_calendar(url)` が **ページ上の全年×確定/予定を取得**し、既存CSVへ**日付キーでマージ**（他年を消さない＝**複数年蓄積**）。当年限定にしない（翌年が JPX で公開され次第、更新を押せば追加。実測で 2026＋2027 を取得）。
- **CSV フォーマット**（`data/market_Calendar.csv`・utf-8-sig・**後方互換＝旧 `date,name,status` も読める**）：

### C.2 tick 取込（`update_ohlc`）
```
now_open = is_market_open()
with lock:                                    # ★引け板寄せ判定は必ず lock 内（bar_end を別スレッド
                                              #   _timer_check が前進させ得る＝lock 外読みは幽霊足の競合）
  # ★引け板寄せ tick（2026-06-26）：セッション末足の終端(15:45/6:00)を越えて最初に届く約定＝実引け値。
  #   クローズ扱いでもこの1本だけ受け入れ、実引け値で板寄せ特別足を立てる（→ §C.3③・§C.4）。
  is_closing_auction = (not now_open) and _is_session_close(bar_end) and (tick_time >= bar_end)
  if (not now_open) and (not is_closing_auction): return
latest_price = price; last_tick_time = tick_time
if is_closing_auction:
    closing_ts = bar_end
    _emit_current_or_dummy()                  # 〜引けの通常足を締める（close=引け直前値）
    _emit_closing_auction(closing_ts, price)  # ★板寄せ特別足＝実際の引け値
    bar_start, bar_end = get_bar_times(tick_time)   # 窓を次セッションへ
    if on_tick: on_tick(price, tick_time)
    return
# 通常 tick：
# ① 出来高は売買高時刻(volume_time)バーへ先行加算（ロール前・二重計上防止／§C.冒頭 2026-06-24）
# ② 価格バーのロール（価格時刻 tick_time 基準・データ時刻ロール）：tick_time>=bar_end の間 _emit して窓前進
# 【seam】リアルタイム broker へ on_tick(price, tick_time)（確定足経路は無傷）
if not (bar_start <= tick_time < bar_end): return
# ③ OHLC を価格時刻バーへ（出来高は①で計上済なら二重計上しない）
if current_candle is None: current_candle = {datetime:bar_start, O=H=L=C=price, V=vol}
else: high=max; low=min; close=price; volume+=vol
```

### C.3 確定（`finalize_candle` / 壁時計フォールバック）— 3種の足
通常はデータ時刻ロール（`update_ohlc` 内）が確定する。tick が来ない静かな窓・引けでは、壁時計の `bar_timer_loop` が1秒ごとに `_timer_check(now)` を呼んで「バー終端＋猶予」を過ぎた足を確定する。

**★2026-06-26 改訂のゲート（最重要）**：旧版は `bar_timer_loop` 冒頭で `if not is_market_open(): continue` していたため、**引けの瞬間（15:45/6:00）は市場クローズ扱いで確定処理ごとスキップ**され、セッション末足＝板寄せ特別足が出なかった。改訂版は **`_is_session_close(bar_end_time)` または `is_market_open()` が真なら確定**する。セッション末では **`AUCTION_WAIT_SEC`（=12秒）まで実引け値 tick（§C.2）を待ち**、届けば update_ohlc 経路が実引け値で板寄せを立てる（このフォールバックは走らない）。届かない静かな引けのみ、ここが `latest_price`（引け直前値）でフォールバック確定する。セッション末でない通常足はクローズ中に確定しない（ゲート過拡張の防止＝§J-1 T11）。`finalize_candle` の旧 `sleep(10)` は lock 保持で tick を遮断し待ちが空振りしていたため撤去（待ちは上記タイマーが非ブロッキングに担う）。
```
# bar_timer_loop（1秒毎）→ _timer_check(now):   ※呼び出し側で lock 済み
if bar_end_time is None: return
if now < bar_end_time + FINALIZE_GRACE_SEC(=3秒): return
if _is_session_close(bar_end_time):
    already = (_last_auction_dt == bar_end_time)             # 実引け値 tick が既に板寄せを立てた
    if (not already) and now < bar_end_time + AUCTION_WAIT_SEC(=12秒): return  # 実引け値 tick を待つ
    finalize_candle(); bar_start, bar_end = get_bar_times(now)   # 猶予超過 or 発火済→確定・窓前進
elif is_market_open():
    finalize_candle(); bar_start, bar_end = get_bar_times(now)   # 通常のフォールバック確定

# finalize_candle():                            # 非ブロッキング（sleep なし）
_emit_current_or_dummy()                       # ①通常確定足 or ②ダミー足（下記）
if (not executed_time) and _is_session_close(bar_end_time):   # ③★板寄せ特別足（フォールバック＝latest_price）
    executed_time = True
    try:
        _emit_closing_auction(bar_end_time, latest_price)
    finally:
        executed_time = False                  # ★必ず戻す（無いと翌日発火しない・既知バグ②）

# _emit_current_or_dummy():                    # データ時刻ロール／壁時計の共通処理（板寄せは含まない）
if current_candle is not None:                 # ① 通常確定足
    add_to_candle(bar); mark_completed(); current_candle=None; fire(bar)
else:
    if not is_market_open(): return
    last = storage.get_last_bar()
    if last is not None:                       # ② ダミー足（静かな窓・前足closeでフラット）
        add_to_candle({datetime:bar_start, O=H=L=C=last.close, V=0}); mark_completed(); fire(dummy)

# _emit_closing_auction(ts, price):            # ③ 板寄せ特別足の生成（二重発火防止つき）
if (not price) or ts is None: return
if _last_auction_dt == ts: return              # ★同一引けは一度だけ（壁時計／データ時刻ロール競合対策）
sp = {datetime: ts, O=H=L=C=price, V=volume}   # ★引け板寄せ出来高（引け tick の volume・2026-06-26）。tick無しの静かな引けのみ V=0
add_to_candle(sp); mark_completed(); _last_auction_dt = ts; fire(sp)
```

### C.4 セッション末足（板寄せ特別足）の不変点 ★絶対遵守（2026-06-26 改訂）
1. **発火判定は「確定足の終端がセッション末か」**＝`_is_session_close(bar_end_time)`（`bar_end_time.time() ∈ {DAY_END(15:45), NIGHT_END(6:00)}`）。**時刻は決め打ちせず市場時間の単一ソースから導出**（§C.1）。旧版の「壁時計の分が 15:45/6:00 ちょうど」判定は廃止（壁時計依存だと引けのクローズ遷移で取りこぼした）。
2. **引けの瞬間に市場クローズ扱いになってもセッション末足は必ず確定する**（`_timer_check` のゲートが `_is_session_close(...)` を含む＋`update_ohlc` の引け板寄せ tick 経路）。これが「15:45/6:00 足が出ない」欠陥の是正点。
3. **板寄せ価格は実際の引け板寄せ約定値**（2026-06-26・ユーザー当初設計）：セッション末足の終端を越えて最初に届く約定 tick を `update_ohlc` がクローズ扱いでも1本だけ受け入れ、その価格で特別足を立てる（§C.2）。実引け値 tick が `AUCTION_WAIT_SEC`(=12秒) 内に届かない静かな引けのみ、`latest_price`（引け直前値）でフォールバック（§C.3 `_timer_check`）。旧 `sleep(10)` は lock 保持で tick を遮断し空振りしていたため撤去。
4. 特別足の **`datetime` は `bar_end_time`**（セッション境界そのもの。直前の通常足と同時刻にならないよう境界で立てる）。O=H=L=C=板寄せ価格。**★V＝引け板寄せ出来高（引け板寄せ tick の volume）＝0固定にしない（2026-06-26）**。TradeStation/TV と同じく板寄せ足にも実出来高があり、CMF 等の出来高戦略が引け判断に正しい出来高を使えるようにする。引け tick が来ない静かな引けのみ V=0（マージで上書きされる）。
5. **二重発火防止＝`_last_auction_dt`（同一引けの `bar_end_time` は一度だけ）＋ `executed_time` を `finally` で必ず False**。latest_price が無い日でも False に戻す（戻さないと翌営業日に板寄せ足が出ない＝ユーザーが最も苦労した固着バグ②）。
6. この足も `on_bar_close` を発火する＝**戦略はセッション末足でも判断する**（SQ クローズ・引け対応に効く）。
7. **リファクタ時も観測挙動を変えない**：セッション末で板寄せ特別足が必ず1本（datetime=bar_end・O=H=L=C=引け値・**V=引け板寄せ出来高**）出ること、実引け値 tick の優先（フォールバックは引け直前値・V=0）、`executed_time`/`_last_auction_dt` の戻し・抑止、境界クランプを保つ。テスト §J-1（T4・T10〜T14）で固定。

|---|---|---|---|---|
| flat | long/short | buy/sell | 新規 | contracts=size, position_size=size |
| long/short(n) | flat | sell/buy | 全量返済 | contracts=n, position_size=0 |
| long(n)→long(m<n) / short 同 | sell/buy | **部分返済（3Split）** | contracts=n−m, position_size=m |
| short→long / long→short | buy/sell | ドテン | prev 記録 |
| 同一 | 同一 | — | 変化なし（送らない） |

### G.1-b ★型：エンジン内部は整数、送信する JSON の `interval` だけ文字列（2026-08-17 確定）

**ブリッジの受信 DTO は `RawWebhookPayload.Interval` が `string?`** で、受け取ってから
`SignalPayloadParser.ParseInterval()` で数値へ変換する作り。**TradingView が `interval` を文字列で
送るのに合わせた形**であり、これがブリッジ側の正。数値で送ると受信時点で
`The JSON value could not be converted to System.String` となり **HTTP 400** で弾かれる。

したがって webhook の組み立てでは **送信直前にだけ文字列化**する。

```python
"interval": str(int(interval)),   # webhook_converter.py。int() で正規化してから文字列に
```

| 場所 | 型 |
|---|---|
| `registered.json` の `interval` / `RealtimeBroker.interval` / `MANIFEST["interval"]` / 画面表示 | **整数** |
| **ブリッジへ送る JSON の `interval`** | **文字列**（"15"） |

エンジン内部で `interval` を比較・計算・分岐に使う箇所は整数のまま。payload の `interval` を
読む処理は存在しない（`fmt_trade` も参照しない）ため、文字列化の影響は送信 JSON の表記のみ。

> **事故の記録（2026-08-17）**：`"interval": int(interval)` で送っていたため、本番初送出の
> `srpf1_local` が `注文エラー HTTP Error 400: Bad Request` で不達。原因は
> `webhook-api-spec.md` の Pine テンプレートが `"interval": {{interval}}`（**引用符なし**）
> と書かれており、それに合わせて数値で実装したこと。**仕様書の記載が実装と食い違っている**
> （同じ誤記が配布版3ファイルとブログにも存在）。

### G.2 order_price ★2026-08-18 全面改訂（不達事故の是正）

**`order_price` には必ず「実際に約定した値段」を入れる。0 を送ってはならない。**

| 遷移 | 載せる値 | 実装 |
|---|---|---|
| 新規・ドテン | 建値 `PineBroker.avg_price` | `RealtimeBroker._fill_price()` |
| 部分返済・全量返済 | 直近 fill の `exit_price` | 同上 |
| いずれも取れないとき | 直近の終値 `_last_close` | 同上 |

- **丸めは行わない。** 値の出どころは足の OHLC（市場の値＝もともと呼値単位）と、
  `PineBroker.submit` 時に `_round_tick` 済みの limit/stop だけ。ここで丸め直すと
  TradingView（`{{strategy.order.price}}` をそのまま送る）と挙動が変わる。

> **旧仕様（誤り）**：「成行＝0（ブリッジが対等価格執行）」。
> ブリッジは `order_price=0` を **BestMarket（対当）** と解釈するが、kabu 仕様では対当も
> **指値**（`FrontOrderType=20`）であり、**値段を入れる処理はブリッジの手動発注の経路にしか無い**。
> シグナル経路は受け取った値をそのまま指値価格として渡すため、0 だと
> **`FrontOrderType=20` / `Price=0`** となり kabu が
> **「パラメータ不正：値段指定エラー」(4002017)** で必ず拒否する。
> 2026-08-18 13:30、`srpf1_local` の新規 Long×3 がこれで不達となった。
> TradingView 版は `{{strategy.order.price}}` に実値が入るため、この穴を踏まない。

### G.2-b ★webhook のフォーマットは TradingView と同一（2026-08-18 統一）

キー・並び・型を TradingView のアラート本文にそろえる（`webhook_converter.py`）。

```json
{"passphrase":…, "alert_name":…, "time":…, "exchange":…, "ticker":…, "interval":…,
 "bar":{"time":…,"open":…,"high":…,"low":…,"close":…,"volume":…},
 "strategy":{"position_size":…,"order_action":…,"order_contracts":…,"order_price":…,
             "order_id":…,"market_position":…,"market_position_size":…,
             "prev_market_position":…,"prev_market_position_size":…}}
```

| 項目 | 値 | 根拠（TradingView 公式） |
|---|---|---|
| `time` / `bar.time` | **UTC・`yyyy-MM-ddTHH:mm:ssZ`** | 「{{time}} is in UTC, formatted as yyyy-MM-ddTHH:mm:ssZ」。ローカルの足時刻は日本時間なので変換する（`to_tv_time()`） |
| `ticker` | **`NK225M1!`**（取引所の接頭辞を**含まない**） | 「ticker of the symbol used in alert (AAPL, BTCUSD, etc.)」 |
| `exchange` | **`OSE`** | 「exchange of the symbol used in alert (NASDAQ, NYSE, CME, etc)」 |
| `bar` | 直近の確定足 OHLCV | `on_bar_close` で `_last_bar` に保持 |
| `strategy.position_size` | **符号付き**建玉数（`+3` / `-3` / `0`） | TradingView と同じ |
| `strategy.order_id` | 決済＝発火した建ち注文の名前（`TP1_C` / `PSTOP` 等）／新規・ドテン＝`entry_<trade_id>` | `{{strategy.order.id}}` 相当 |

※ ブリッジが読むのは `passphrase` / `alert_name` / `interval` / `ticker` と `strategy` 配下の
7 項目のみ（`RawWebhookPayload.cs`）。他は読まれないが、**仕様が「TradingView と同一」**のためそろえる。
「ブリッジが読まないから合わせなくてよい」という判断はしない（ブリッジ側の仕様が変われば壊れる）。

### G.2-c ★送出内容は必ずログに残す（2026-08-18）

`RealtimeBroker._emit` の DBG が `wh.get('order_action')` のように**トップレベル**を見ており、
実際は `wh["strategy"]` 配下のため **常に `None xNone @-`** としか出力されず、
**何を送ったのかログから追えなかった**（8/18 の不達調査で判明）。参照先を修正し、
送出するものは**全文を DBG に残す**（`passphrase` は伏字）。

### G.3 dry-run シンク
- `BridgeSender` を `VirtualSink` に差替：webhook を POST せず、仮想建玉に適用→仮想損益・シグナル行をログ/画面。送出以外（戦略・broker・feed）は本番同一＝挙動を正確に観測。

## K. 実装で確定した運用挙動（v2.0 追補・2026-06-16）

ダッシュボード運用で確定した挙動（実装＝本節）。背景は `docs/devlog/2026-06-16.md`。

- **K.1 ★dry-run/仮想モード廃止＝記録常時＋送出は戦略ごと（2026-06-18 改訂）**：旧「仮想トレードON/OFF（グローバル dry-run）」は撤去。**記録は全戦略・常時**（enabled 不問・`_processing`＝ready全戦略）、**送出は戦略の enabled のみ**（有効＝`sender=BridgeSender`／無効＝`sender=None`）。起動/停止/仮想トグルの各ボタンも廃止し**ダッシュボード起動＝自動運用開始**。停止＝enabled を外す／ブリッジ停止／窓を閉じる。記録 mode＝有効「本番」/無効「仮想」（フォーマット不変）。
- **K.2 tick入口の接続タイミング**：feed（`LiveFeed`・TCP5000 サーバ）は**ダッシュボード起動時（`_auto_start`）に接続開始**。停止/閉じるで切断。ブリッジの `AiTickForwarder` は**クライアントで3秒ごとに5000へ再接続**（→ feed 待受開始で自動接続）。
- **K.3 ★ポート安全制御（使用中なら接続しない）**：`LiveFeed.start()` は**同期 bind（SO_REUSEADDR 無し）**で 5000 が使用中なら `False`＝**接続しない**（本番tick経路を壊さない）。`controller.start()`/`run_live`/ダッシュボードは feed 失敗時に**起動中止＋警告**。
- **K.4 ブリッジ二重起動防止**：`BridgeProcess.is_up()`＝**webhookポート8001で起動中を判定（手動起動も検知）**。起動中は[ブリッジ起動]disable。**停止はダッシュボード起動分のみ**（手動起動は手動停止）。
- **K.5 売買シグナルのログ形式**：`bridge_sender.fmt_trade` で統一＝`[売買・仮想] <短名> 買い×N (prev→cur)` ／ `[売買・本番] … → outcome`。ダッシュボードは「`[売買`」を**緑タグ**表示。feed/接続ログは sink でログ欄へ。
- **K.6 manifest 一貫化**：登録時に `manifest.json` が無ければ `MANIFEST` から自動生成（ZIP/フォルダ登録どちらも保持）。
- **K.7 配布ZIP**：開発者ツール `N225StrategyBuilder/distribution/package_strategy.py`（GUI）で確定戦略フォルダ→ZIP（manifest自動生成）。LocalEngine の `resolve_package`（自動解凍→`strategy.py`検出→登録）と互換。
- **K.8 安全運用（本番稼働中）**：本番トレード版が動作中は LocalEngine の起動・ソケット接続・ブリッジ操作を**ユーザーが安全なタイミングで**行う（tick入口5000は排他＝local+TV同時はB案分配が要・当面A排他）。
- **K.9 起動の高速化（2026-06-18）**：起動が warmup で遅かった（5戦略×500本≒28秒）。対策＝**①ウィンドウを先に表示し warmup はバックグラウンドスレッドで実行**（`dashboard._auto_start`・完了まで `running=False`＝注文しない）＋**②warmup を manifest 宣言値（300本）に短縮**（`controller.start` が `warmup_df.tail(warmup_bars)` を prime）。実測 28秒→約11秒。warmup の重さは戦略の指標毎バッファ再計算が主因（さらなる高速化は戦略側の最適化が必要）。
- **K.10 UI レイアウト（2026-06-18）**：ヘッダー＝タイトル左／設定・LED・時計を右に寄せる。カードは①戦略・②ブリッジの2枚（③オートトレードカードは廃止）。各カードのボタンは2列で幅統一。登録一覧は6行表示（超過はスクロール）。窓は約 880×520（最小 820×480）。②注記＝「KABUステーション→ブリッジ起動／注文は戦略有効✓のみ」。
