## 1. 全体スレッドモデル

**プロセス構成:**
- **メインプロセス（ダッシュボード or run_live）**: GUI/ヘッドレスのエントリポイント。単一インスタンス Mutex ガード。
- **複数の背景スレッド**: ライブトレード処理、GUI 重処理、ファイルI/O、送信。

**単一インスタンスガード:**
- ファイル: `app/instance_lock.py`
- Windows 名前付き Mutex「N225AutoTraderLocalEngine」で dashboard と run_live を相互排他。
- 目的: TCP :5000 ポート競合の根絶（2026-06-23 の事故対策）。

**設計原則（2026-07-02 完成）: 「受信スレッドは積むだけ・計算/送信/保守は各専用ワーカー」**

## 2. ライブ実行（トレード処理）のスレッド構成

| スレッド | 役割 | 起動元 |
|---------|------|-------|
| メインスレッド | GUI（tkinter）or コンソール | 起動時 |
| TCP受信スレッド | ブリッジからの tick 受信（TCP :5000） | feed.start() |
| TCP接続ハンドラ（複数） | 各接続の tick パース → **ディスパッチキューへ enqueue のみ** | 接続ごと |
| OHLC確定タイマー | 確定足の壁時計フォールバック → **enqueue のみ** | feed.start_ohlc_timer() |
| **★le-dispatch（新設 07-02）** | **tick/確定足の fan-out（全戦略の on_tick / on_bar_close）を単一キューから直列処理** | 初回 enqueue 時（lazy） |
| **★bridge-send（新設 07-02）** | **注文 webhook の HTTP POST（共有 FIFO キュー・全戦略の送信順序を保存）** | 初回 send 時（lazy） |
| Parquet保存ワーカー | 確定足を parquet へ永続化 | 確定足ごと |
| ダッシュボード・ポーラー | kabu/ブリッジ状態の定期チェック（3秒毎） | _start_poller() |
| **★le-rewarm（新設 07-02）** | 稼働中 load_all の全戦略再warmup（背景） | load_all（was_running時） |
| **★le-reload-\<名\>（新設 07-02）** | 差分リロード＝1戦略のみの再構築（背景） | reload_one() |
| **★bridge-stop（新設 07-02）** | ブリッジ停止の terminate→wait（最悪8秒）を背景化 | stop_bridge() |

**ライブ処理の流れ（07-02 改修後）:**
1. **tick受信**（TCP接続スレッド）: JSON パース → `OHLCManager.update_ohlc()`（lock 保護）→ `engine.on_tick()` は**キューに積むだけ（実測 0.005ms/件）**。
2. **確定足生成**（タイマー or データ時刻ロール）: `finalize_candle()` → `engine.on_confirmed_bar()` も**キューに積むだけ（実測 1ms）**。建玉スナップショット保存は after コールバックとして同キューに乗る（fan-out 完了後に実行＝順序維持）。
3. **fan-out（le-dispatch ワーカー）**: 単一キューから tick/確定足を**到着順に直列処理**。各 RealtimeBroker の on_tick / on_bar_close を順次実行。1確定足の全戦略処理＝実測 約100ms／15分（使用率 0.01%）＝戦略数10倍でも余裕。
4. **注文送出**: RealtimeBroker がシグナル → `BridgeSender.send()` は**共有キューに積んで即返る**。bridge-send ワーカーが同期 POST（timeout 5秒）を実行。**ブリッジが遅くても feed/fan-out は一切止まらない**（旧実装＝最大5秒×シグナル数のフィード停止リスク）。

**★重要な副次効果**: 旧実装では「TCP受信スレッド（tick）」と「OHLCタイマースレッド（確定足）」が
**同じ RealtimeBroker に同時侵入し得る競合窓**があったが、両方が le-dispatch の単一キュー経由に
なったことで**構造的に解消**（直列化・FIFO で到着順も保存）。

**キュー満杯時の方針**: 確定足＝原則落とさない（2秒待って警告ログ）／tick＝破棄（最新性優先・次 tick で追いつく）。

## 4. ①③④の核心：差分リロード reload_one（従来 load_all の置換）

稼働中の登録追加・登録編集・パラメータ保存は `controller.reload_one(name)` を通る：

1. **旧実体は生かしたまま**、当該戦略だけを背景スレッドでフレッシュ読込（config.json 再読込）→ warmup-replay で履歴から再構築（建玉・指標バッファ・出口状態を復元）。
2. 再構築が完成してから `LiveEngine.upsert()` で**原子的に差替**（新 dict を作って参照ごとスワップ＝le-dispatch の列挙と競合しない）。**差替は一瞬・他戦略と engine.running は終始無影響**。
3. 再構築中は `sender=None` で過去足の誤 Webhook を送らない／建玉が残れば warmup 不足でも強制 ready=True（出口管理を必ず継続）＝従来の安全動作を継承。
4. 実測：呼出 1ms・差替完了 約7秒（1戦略）／旧実装＝**全戦略停止で42秒＋GUIフリーズ**。
5. `_rewarm_lock` で全体再warmup・他の差分と直列化。全体 `load_all()` 側も同様に背景化済（世代チェック＝連続保存は最後が勝つ・`_rewarm_active` フラグで進行中の連続保存も正しく扱う）。

**②削除（unregister）は従来どおり:**
- `engine.remove(name)` で当該 broker を辞書から落とすだけ。他戦略には無影響。
- **ただし `remove` は建玉を決済しない。** 建玉を持った戦略を削除すると実ポジションが管理放棄される（削除前に手仕舞いすること）。

## 6. 競合・ブロッキングのリスク評価（07-02 改修後）

### 解消済み（07-02）
- ①③④の GUI フリーズ（42秒） → 差分リロードで解消（呼出1ms・他戦略無停止）
- 注文送信の同期 HTTP がフィード系スレッドを最大5秒×件数ブロック → 送信キュー化で解消
- tick 受信スレッドとバータイマースレッドの同一ブローカー同時侵入窓 → 単一ディスパッチワーカーで解消
- ①③④のリロード窓（全戦略 running=False の数十秒） → 差分は他戦略無停止・対象戦略も差替一瞬のみ

### ⚠ 残る注意（低リスク）
1. **trade_log.jsonl の読み書き競合（⑦）**: 確定足直後に[取引記録]を開くと理論上 JSONL 行の途中読みがあり得る（低確率）。改善候補＝lock or 一時コピー読み。
2. **②削除時の建玉放棄**: 建玉のある戦略の削除は避ける（無効化して手仕舞い後に削除）。
3. **差分リロードの取りこぼし窓**: warmup df スナップショット後〜差替までの間に確定した足（数秒窓・15分足では稀）は新実体に反映されない。従来の全体再warmupにも同じ窓があった（悪化ではない）。
4. **ワーカー停滞**: le-dispatch が万一停滞するとキュー滞留（確定足は警告ログ「dispatch キュー満杯」で可視化・要再起動）。

## 7. GIL による暗黙の直列化

CPython は GIL で bytecode 実行が直列化されるため、以下は事実上 lock 不要:
- bool/int の読み書き（`engine.running` 等）／dict の単一 key 参照・**参照スワップ**（upsert）
- 単一行のファイル write

GIL で保護されないもの → 個別に保護済み:
- parquet 読み書き（numpy/pandas が GIL release）→ ohlc_storage の lock
- read→parse→append の複合操作 → trade_log.jsonl が未保護（残課題）

| 機能 | トレード中の操作 | 並行性 |
|------|-----------------|--------|
| ①戦略追加 | OK（GUI 固まらず・他戦略無停止） | 差分リロード（背景） |
| ②削除 | フラットな戦略なら OK | 軽量同期・建玉放棄に注意 |
| ③登録編集 | OK | ①と同等 |
| ④パラメータ | OK | ①と同等 |
| ⑤バックテスト | OK | 完全独立（従来から） |
| ⑥データ管理 | OK | 完全独立（従来から） |
| ⑦取引記録 | OK | 潜在競合（低確率・残課題） |
| ⑧カレンダー | OK | 完全独立（従来から） |

**全体評価**: 「受信スレッドは積むだけ／計算＝le-dispatch／送信＝bridge-send／保守＝le-rewarm・le-reload」
の責務分離が完成。フィード受信と記録はいかなる GUI 操作・ブリッジ遅延でも止まらない。
戦略数のスケール限界は fan-out 実測 約100ms/15分（6戦略・使用率0.01%）から見て実用上遠い。

**残る改善候補:**
1. `read_trade_log()` の lock 保護（or 一時コピー読込）。
2. ②削除時、建玉のある戦略への警告 or 自動フラット。
